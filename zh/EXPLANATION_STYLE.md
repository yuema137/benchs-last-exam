# 解释风格指南

## 目标

解释评测概念时，要让一个有技术好奇心的读者能够理解：发生了什么变化、为什么重要、一个数字是如何产生的，以及结论到哪里为止。

对 Observatory 而言，尤其要始终把“benchmark 分数说明了什么”与“我们是否有足够强的 probe 去知道它”区分开来。在下 lifecycle 结论之前，先解释 coverage。

## 必需的结构

对于一个信息密集的概念，在有帮助时按以下顺序展开：

1. 陈述那个实际问题。
2. 点明 actor、object 和被改变的步骤。
3. 展示前后的机制或数据流。
4. 给出一个小的、用到真实 schema 字段、公式或一小段 trace 的示例。
5. 说明边界、caveat，以及该结果并未确立什么。

优先使用因果句，而非抽象名词的堆砌。在术语第一次有意义地出现时解释它，之后一致地使用稳定的项目 label。

## DongbeiGPT 原则

DongbeiGPT 是一种把话讲清楚的纪律，而不是一件方言戏服。在直接的中文解释中：

- 使用平实、具体的措辞；
- 在语境允许时保持放松的对话节奏；
- 在给出某个字段或 metric 的名字之前，先说清它实际做什么；
- 当一种关系容易被误解时，用一个精简的例子；
- 精确地保留技术术语、公式和各种区分；
- 一旦口语化标记会降低精确性或可理解性，就把它去掉；
- 避免地域词汇、口音表演、玩笑和空洞的亲热。

对于正式文档、方法学、schema、测试和代码，保持所要求的专业风格。本风格指南管辖的是解释的组织方式和清晰度；它并不授权更改技术 claim。

## 双语规则

英文页面是 canonical。中文页面必须保留相同的信息和证据，同时读起来是自然的中文。翻译含义，而非语序。不要翻译标识符、benchmark 名称、论文标题、公式、URL 或代码字面量。
